# 시간과 실제 진행 상태로 다음 작업 고르기

180분은 계획 기준이다. 잔여 시간은 참가자가 화면에서 확인해 알려준 값만 사용한다. 이전 보고는 계속 ‘마지막 보고’이며 도구 실행 시각·호스트 시계로 갱신하지 않는다.

## 시간대별 기본 권고

| 경과 | 남은 시간 | 기본 초점 | 전환 조건·다음 행동 |
|---|---|---|---|
| 0~8 | 180~172 | 과제·자료 확인 | 사용자·입력·필수 결과·기존 실행 방법 파악 |
| 8~20 | 172~160 | 업무 사례 | 목표·큰 오판·사람의 책임 확인 |
| 20~30 | 160~150 | 규칙·예외 | 조건·기대 처리·성공 기준으로 재진술 |
| 30~40 | 150~140 | 최소 설계 | 입력·규칙·상태·표시·실패 책임을 필요한 수준으로 구분 |
| 40~65 | 140~115 | 첫 프로토타입 | 사용자 행동 하나를 입력부터 결과까지 연결 |
| 65~80 | 115~100 | 직접 사용·규칙 검사 | 입력·기대·실제 차이로 문제를 재현 |
| 80~105 | 100~75 | 개선 | 원인 확인→최소 수정→같은 반례와 영향 검사 |
| 105~125 | 75~55 | 필수 흐름 완성 | 실제 요구의 저장·출력·전달·실패 처리를 연결 |
| 125~145 | 55~35 | 통합 검증 | 필수 요구·중요 예외별 통과·실패·미검증 확인 |
| 145~165 | 35~15 | 본인 설명·일치 확인 | 실제 구조·선택 이유·실패 조건을 코드와 대조 |
| 165~180 | 15~0 | 저장·제출 | 새 기능 중단, 실제 최종 상태·파일·제출 확인 |

정확한 경계 시점은 다음 구간으로 넘어간다. 예: 남은 115분이면 첫 프로토타입 시간은 지났고 직접 사용·검증 권고다. **시간 구간은 실제 기능 완료를 뜻하지 않는다.** 후속 서술형 시간은 이 180분 표에 포함하지 않는다.

## 실제 상태가 시간표와 다를 때

| 관찰 | 다음 한 작업 |
|---|---|
| 과제에 규칙과 성공 기준이 이미 명시됨 | 근거만 기록하고 인터뷰를 줄여 작은 흐름 구현 |
| 정책 미확인이 잘못된 자동 결정을 만들 수 있음 | 참가자에게 해당 정책 질문, 독립적인 부분 구현, 위험 결정은 임의 확정 금지 |
| 프로토타입 구간이 지났지만 흐름이 연결되지 않음 | 확장·미관 중단, 입력 한 건의 전체 경로 연결 |
| 반례가 기존 정책을 위반함 | 담당자에게 같은 질문을 반복하기보다 코드 재현·원인 확인 |
| 새 업무 경계가 드러남 | 코드 수정 전 해당 처리 정책 확인 |
| 핵심 경로가 실패함 | 부가 기능보다 재현·원인·최소 수정·회귀 검사 |
| 남은 35분 이하이고 요구가 충족됨 | 설명·실제 코드·검증 기록 대조, 새 아키텍처 보류 |
| 남은 15분 이하 | 새 기능 중단. 제출을 막는 결함의 가능한 최소 수정, 저장·실행·제출 확인 |
| 잔여 0분 또는 AI 금지 후속 단계 | 작업 중단. 후속 문항 분석·답안 지원 금지 |

사용자가 시간이 늘었다고 명시 보고하면 정정으로 기록한다. 예전 단계부터 재시작하거나 이미 확인한 정책을 다시 묻지 않는다. 이전 시간과 상충하는 보고를 AI가 임의 보정하지 않는다.

## 상황별 짧은 위임 예시

### 담당자 답변을 받았을 때

```text
답변의 확인된 규칙·근거·미확인을 나누고 바뀐 MD 행만 갱신한다.
각 규칙을 기능·필요 조건·예외·관찰 가능한 성공 기준으로 연결한다.
기존 정책과 충돌하면 표시하고, 내 판단 이유를 만들지 않는다.
```

### 작은 흐름 구현

```text
확인된 정책 안에서 [기능 ID]를 구현한다.
관련 코드·입력·검사를 먼저 확인하고 변경 경계를 정한다.
정책·저장 범위·권한 변경은 영향과 대안을 알린다.
정상·업무 반례를 검사하고 실행한 범위와 미검증을 반환한다.
```

### 실패와 수정 제안

```text
같은 입력으로 실패를 재현하고 어느 경계에서 달라지는지 확인한다.
제안은 실제 문제·근거·영향·반례·작은 대안·검증에 대조한다.
원인을 확인한 뒤 최소 수정하고 같은 반례와 영향 검사를 실행한다.
제안 자체나 다른 AI의 동의를 실행 근거로 취급하지 않는다.
```

### 통합 검증과 이해 점검

```text
필수 요구와 중요한 예외를 실제 구현·실행 근거에 대조한다.
빌드·규칙 검사·직접 UI·저장 복구를 구분한다.
참가자의 설명과 다른 실제 파일·함수·상태·한계를 지적한다.
참가자가 밝히지 않은 선택 이유나 후속 서술형 답안을 만들지 않는다.
```

## 단계별 실제 연결

원본은 팩에 함께 포함된다. [skill-routing.md](skill-routing.md)의 경로·실행 계약을 적용하고 각 연결 스킬과 지정 원본을 읽는다.

| 경과·실제 상태 | 적용 경로 |
|---|---|
| 0~8 자료 조사 | 기본 파일·코드 도구로 과제 확인; 필요하면 interview 진입 |
| 8~30 담당자 사례·규칙·예외 | sk-exam-interview |
| 30~40 최소 설계·작업 계획 | sk-exam-design → sk-exam-plan |
| 40~65 첫 흐름 구현 | sk-exam-implement ↔ sk-exam-test |
| 65~80 직접 사용·반례 검사 | sk-exam-test, 실패 시 sk-exam-debug |
| 80~105 개선 | sk-exam-debug → sk-exam-implement/test; 중요 제안이면 review-response |
| 105~125 필수 흐름 연결 | sk-exam-implement/test |
| 125~145 통합 변경 검토 | sk-exam-review → 필요한 수정·재검사 → sk-exam-verify |
| 145~165 실제 구조·설명 일치 | sk-exam-verify; 새 정책 공백이면 해당 부분 interview |
| 165~180 저장·최종 상태 | sk-exam-verify 우선; 제출을 막는 결함만 최소 debug/test |

위 경로는 권고다. 실제 완료를 시간만으로 가정하지 않는다. 원본 런타임 전체 실행·모든 gate 통과와 시험용 제한 적용을 구분한다. 원본의 설치·외부 통신·작업공간 전환·자동 제출을 실행하지 않는다.
