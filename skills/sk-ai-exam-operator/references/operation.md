# 시간 운영: 구현 → 검토 → 문서화 구간

세 역할을 세 세션으로 나눠 쓰면 아래 구간은 **세션 1의 시간표**이고, 세션 2·3이 언제 무게를 싣는지의 기준이다. 역할별 절차·파일 소유권은 [roles.md](roles.md)를 따른다. 세 세션이면 세션 1은 검토 구간(100~150)에 검산기를 따로 만들지 않고 세션 2의 발견(R)을 반영·보강하며, 기록은 아래 표 대신 세션 1은 `10_work_log.md`, 세션 2는 `20_review.md`, 세션 3이 01~06에 쓴다. 세션을 하나만 쓸 수 있으면 한 세션이 아래 구간을 차례로 맡는다.

180분은 계획 기준이다. 잔여 시간은 참가자가 화면에서 확인해 알려준 값만 사용한다. 이전 보고는 계속 ‘마지막 보고’이며 도구 실행 시각·호스트 시계로 갱신하지 않는다. 후속 서술형 시간은 이 180분에 포함하지 않는다.

## 구간 한눈에 보기

| 구간 | 경과 | 남은 시간 | 목적 | 종료 조건 |
|---|---|---|---|---|
| **1. 메인 구현** | 0~100 | 180~80 | 확인한 업무 규칙으로 필수 기능의 입력→결과를 한 번 끝까지 연결 | 필수 F마다 실제 실행 경로와 실행 기록 T가 하나 이상 있음 |
| **2. 검토·보강** | 100~150 | 80~30 | 구현 구간 결과를 해법과 다른 경로로 검산하고, 찾은 결함·누락을 고침 | 필수 F·중요 E별 통과/실패/미검증 표가 마지막 코드 변경 뒤 실행 결과로 최신 |
| **3. 문서화** | 150~180 | 30~0 | 구현·검토 구간의 실제 기록을 인계 문서로 모으고, 문서의 주장을 코드·검사와 대조 | `06_handoff.md`의 모든 줄에 근거 ID, 저장·실행·제출 확인 |

시작할 때 참가자에게 **구현 구간 종료(개선 중단) 시각**을 남은 시간 기준으로 정하게 한다. 정하지 않으면 남은 80분을 쓴다. 시간 경계는 권고다. **구간 전환은 종료 조건으로 판단하고, 시간이 지났다는 이유만으로 완료 처리하지 않는다.** 다만 아래 두 경계는 시간이 우선한다.

- **남은 30분**: 구현 구간이 끝나지 않았어도 새 기능을 멈추고 문서화 구간으로 간다. 미완 F는 미구현으로 기록한다.
- **남은 15분**: 문서 정리도 줄이고 제출을 막는 결함의 최소 수정·저장·제출 확인만 한다.

## 기록은 구간마다 남기고, 문서화 구간은 모으기만 한다

문서화 구간에서 기억으로 처음 쓰면 실제 로그와 어긋난다. 구현·검토 구간 중에 그때그때 한 줄씩 남긴다.

| 구간 | 바로 남길 것 | 위치 |
|---|---|---|
| 1 | 담당자 답변·규칙(Q), 기능·성공 기준(F), 예외(E), 중요한 AI 설계 제안과 참가자 선택(D), 첫 실행 명령·결과(T) | 01·02·03·04·05 |
| 2 | 독립 검산·반례 결과(T), 실패→원인→수정→재검사, 리뷰 발견, AI 수정 제안 심사(D), 조건 변경 재실행 결과 | 03·04·05 |
| 3 | 위 기록을 `06_handoff.md`로 모음. 새 사실·이유를 만들지 않음 | 06 |

## 1. 메인 구현 (경과 0~100)

| 경과 | 초점 | 적용 경로 | 다음으로 넘어가는 조건 |
|---|---|---|---|
| 0~8 | 과제·자료 확인, 문제 지도(15분 안팎, 인터뷰 준비와 겹침) | 기본 파일·코드 도구, `sk-exam-frame`(세 세션이면 세션 3) | 사용자·입력·필수 결과·기존 실행 방법 파악 |
| 8~25 | 담당자 사례·규칙·예외 | `sk-exam-interview` | 목표·핵심 규칙·성공 기준을 조건→처리→예외→성공 기준으로 재진술 |
| 25~35 | 최소 설계·작업 계획 | `sk-exam-design` → `sk-exam-plan` | 입력·규칙·상태·출력·실패 책임과 작업 순서가 정해짐 |
| 35~65 | 첫 end-to-end 흐름 | `sk-exam-implement` ↔ `sk-exam-test` | 사용자 행동 하나가 입력부터 결과 파일·화면까지 실제 실행됨 |
| 65~100 | 필수 기능 완성 | `sk-exam-implement` ↔ `sk-exam-test`, 실패 시 `sk-exam-debug` | 필수 F 전부 실행 경로 + T 기록 |

- **가장 단순한 완주가 먼저다.** 정교한 알고리즘·화면은 첫 흐름이 실제 결과를 낸 뒤에 올린다. 첫 흐름이 65분까지 연결되지 않으면 확장·미관을 멈추고 입력 한 건의 전체 경로부터 잇는다.
- **업무 규칙·계산은 고정 코드로.** 판정·숫자는 모델의 말이 아니라 실행한 코드의 출력으로 말한다.
- 업무 규칙마다 작은 검사를 함께 둔다(규칙 하나 = 검사 하나). 검토 구간의 독립 검산과는 별개다.
- 정책 미확인이 잘못된 자동 결정을 만들 수 있으면 그 부분만 참가자에게 묻고, 독립적인 부분은 계속 구현한다.

## 2. 검토·보강 (경과 100~150)

구현 구간 결과를 **다른 눈으로** 본다. 같은 코드가 같은 가정으로 자기 결과를 확인하는 것, 같은 코드의 재실행, 다른 AI의 동의는 검토가 아니다.

**시작할 때 한 번**: AI에게 "내가 지시하지 않았는데 네가 정한 것을 대안과 함께 모두 나열하라. 코드는 고치지 마라"라고 묻는다. 나온 항목 중 업무 결과를 바꾸는 것만 참가자가 채택·수정·기각하고 `04_decisions.md`에 남긴다. 세 세션이면 세션 2가 작업 로그의 ‘AI가 스스로 정한 것’ 칸과 코드를 대조하고 결과는 `20_review.md`에 남긴다.

**검토 순서**: ① 요구 충족(누락·오해·요구에 없는 추가) → ② 품질·검증(검산·반례·위험). 검토하는 동안에는 결과 파일·코드를 고치지 않고 발견만 모은다. 고치는 것은 그다음 보강 구간에서 한다.

발견 사항은 한 줄씩 같은 형식으로 남긴다.

```text
[발견 ID] 중요도(제출 차단/결과 오류/한계) · 재현됨/의심
요구·근거 ID와 파일:행 · 재현 입력·명령 · 기대 vs 관찰 · 업무 영향 · 최소 수정안
```

재현하지 못한 것은 ‘의심’으로 두고 통과·결함으로 단정하지 않는다.

| 경과 | 초점 | 적용 경로 | 다음으로 넘어가는 조건 |
|---|---|---|---|
| 100~115 | 독립 검산·요구별 검사 | `sk-exam-test` | 필수 F·중요 E마다 해법과 다른 경로의 검사가 있고, 각 검사가 한 번은 실패를 잡는 것을 확인 |
| 115~130 | 통합 리뷰·조건 변경 재실행 | `sk-exam-review` | 요구 누락·정책 불일치 목록, 담당자가 바꿀 값으로 다시 실행한 결과 |
| 130~150 | 결함 보강·재검사·참가자 설명 | `sk-exam-debug`, 중요한 AI 수정 제안은 `sk-exam-review-response` | 발견 결함별 원인 확인→최소 수정→같은 반례 재검사, 마지막 변경 뒤 전체 검사 재실행 |

- **기대값 먼저**: 기대값은 요구·담당자 답변·손계산으로 먼저 정한다. 구현 결과를 보고 기대값을 맞추지 않는다. 검사가 실패하면 검사를 고치기 전에 그 이유를 참가자에게 알리고, 테스트 수정·삭제는 참가자 확인 후에만 한다.
- **독립 검산**: 결과 파일을 읽어 제약을 처음부터 다시 계산한다(용량·한도·누락·중복·시각 등). 해법 모듈을 import해 같은 함수로 확인하지 않는다. 합계가 맞아도 행별 대응은 따로 확인하고, 빈 값을 0이나 정상으로 바꾸지 않는다.
- **실패 먼저**: 일부러 망가뜨린 입력·결과(누락 한 건, 한도 초과, 잘못된 단위 등)로 검사가 FAIL을 내는지 본다. 실패를 한 번도 보지 못한 검사는 통과 근거로 쓰지 않는다.
- **검사할 것이 없으면 통과가 아니다**: 검사 대상이 0건이거나 전부 건너뛰면 미검증으로 둔다.
- **조건 변경 재실행**: 담당자가 운영 중 바꿀 수 있다고 한 값(기준값·용량·한도 등)을 실제로 바꿔 다시 실행하고, 결과가 어떻게 달라지는지와 새로 생기는 실패·제외를 기록한다. 값만 바꾸면 끝나는지, 다른 제약이 함께 움직이는지 확인한다.
- **위험 경계**: 입력 검증·권한·민감 정보 노출·저장 복구 중 과제에 실제로 있는 것만 골라 T에 연결한다.
- **참가자 먼저 설명**: 아래 절차를 검토 구간 끝에 한 번 실시한다. 문서화 구간의 문서가 참가자의 실제 이해와 맞는지 미리 확인하는 단계다.

## 3. 문서화 (경과 150~180)

| 경과 | 초점 | 적용 경로 | 종료 조건 |
|---|---|---|---|
| 150~165 | 기록 정리·주장과 코드 대조 | `sk-exam-verify` | `06_handoff.md` 작성, 각 줄의 근거 ID가 실제 파일·검사와 일치 |
| 165~180 | 저장·실행·제출 확인 | `sk-exam-verify` | 실제 실행 명령 재실행, 파일 저장 확인, 참가자가 제출 상태를 직접 확인 |

- **새 기능 금지.** 문서를 쓰다 결함을 발견하면 제출을 막는 것만 최소 수정하고 같은 검사를 다시 돌린다. 나머지는 ‘감수한 한계’에 적는다.
- `06_handoff.md`는 01~05에서 **복사·요약**한다. 근거가 없는 줄은 `근거 없음`으로 표시하고 지우거나 다시 확인한다. 참가자가 밝히지 않은 이유는 `참가자 이유 미기재`.
- **AI가 한 일과 참가자가 판단·확인한 일을 나눈다.** 검사마다 수행자(AI 실행 / 참가자 관찰)를 적고, 참가자의 판단 기록이 없으면 `기록 없음 · 본인 확인 필요`로 둔다.
- 과거 판단이 바뀌었으면 기존 행을 지우지 말고 정정 행을 새로 추가한다(언제·무엇을 보고 바꿨는지).
- 작업 영역마다 `관련 파일 | 실행한 명령 | 실제 결과(검사 수·핵심 숫자)` 색인을 둔다. 근거 파일로 바로 찾아갈 수 있게 하는 것이 목적이다.
- 남은 시간이 15분보다 많으면, 참가자가 `06_handoff.md`만 보고 "왜 이렇게 했나 / 무엇을 감수했나 / AI 제안을 어떻게 확인했나"를 채팅에 짧게 써 보게 한다(소리 내어 말하게 하지 않는다). 막히는 곳은 기록이 빠진 곳이므로 해당 기록만 보충한다. AI가 모범 답변을 먼저 쓰지 않는다.
- 과제가 README·보고서 등 별도 제출 문서를 요구하면 그 형식이 우선이다. `06_handoff.md`는 그 문서의 재료로 쓰고 중복 문서를 강제하지 않는다.
- 문서의 주장(“모든 대상 처리”, “한도 준수” 등)마다 실제 검사 T를 연결한다. 검사가 없는 주장은 미검증으로 바꾼다.
- 후속 서술형은 AI 금지다. 이 구간은 과제 시간 안의 실제 기록 정리이며 서술형 답안을 미리 쓰지 않는다.

## 실제 상태가 구간 표와 다를 때

| 관찰 | 다음 한 작업 |
|---|---|
| 과제에 규칙과 성공 기준이 이미 명시됨 | 근거만 기록하고 인터뷰를 줄여 구현 구간 첫 흐름으로 |
| 35~65 구간이 지났지만 첫 흐름이 없음 | 확장·미관 중단, 입력 한 건의 전체 경로 연결 |
| 구현 구간이 100분 전에 종료 조건 충족 | 남는 시간을 확장 대신 검토 구간 독립 검산에 사용 |
| 100분이 지났지만 필수 F가 남음 | 남은 F 하나만 최소 구현하고 검토 구간으로. 남은 30분 경계는 넘기지 않음 |
| 검토 구간 검산이 핵심 결과를 깨뜨림 | 재현→원인→최소 수정→같은 반례 재검사. 부가 기능보다 우선 |
| 반례가 기존 정책을 위반함 | 담당자에게 같은 질문을 반복하기보다 코드 재현·원인 확인 |
| 새 업무 경계가 드러남 | 코드 수정 전 해당 처리 정책만 확인 |
| 남은 30분 이하 | 문서화 구간. 새 기능 중단 |
| 남은 15분 이하 | 제출을 막는 결함의 최소 수정, 저장·실행·제출 확인 |
| 잔여 0분 또는 AI 금지 후속 단계 | 작업 중단. 후속 문항 분석·답안 지원 금지 |

사용자가 시간이 늘었다고 명시 보고하면 정정으로 기록한다. 예전 구간부터 재시작하거나 이미 확인한 정책을 다시 묻지 않는다. 이전 시간과 상충하는 보고를 AI가 임의 보정하지 않는다.

## 참가자 먼저 설명

검토 구간 끝(또는 첫 흐름 완성 직후)에 한 번 실시한다. 이미 실제 설명과 코드 대조를 했다면 반복하지 않는다. 남은 15분 이내에는 시작하지 않는다.

1. 현재 구현과 관련된 짧은 질문을 제시한다. 예: “이 입력의 예상 결과, 선택 이유, 실패 조건을 먼저 설명해 주세요.” 이 확인 전에 AI 모범 설명을 보여 주지 않는다.
2. 참가자의 실제 답변을 기다리는 동안 답에 의존하지 않는 검사·기록은 계속한다. 답이 없으면 ‘참가자 설명 미확인’으로 남긴다. 기술적으로 통과한 기능을 참가자 이해까지 확인됐다고 표시하지 않는다.
3. 답변을 실제 파일·함수·상태와 대조한다. 불일치만 근거와 함께 지적하고, 설명의 오류와 구현의 요구 위반을 구분한다. 확인된 정책과 구현이 충돌하면 코드를 고치고 재검사한다(세 세션이면 세션 3은 고치지 않고 세션 1에 반영을 요청한다).
4. 실제 설명·불일치·확인 근거만 `05_verification.md`에 짧게 남긴다. 선택 이유는 참가자가 실제 말한 경우에만 `04_decisions.md`에 연결한다. AI 금지 후속 단계에서는 질문·답변 지원·기록 모두 중단한다.

## 시간·문서 비용

- 이미 명확한 요구를 다시 인터뷰하거나 계획 구간을 채우려고 기다리지 않는다.
- 동일 원본의 재진입은 skill-routing.md의 문맥 재사용 규칙을 따른다. MD는 바뀐 행만 갱신하고, 별도의 이해도·보안·스킬 보고서를 중복 생성하지 않는다.
- 실제 입력 표본이 있으면 누락·중복·단위·형식을 살펴 기대 처리와 연결한다. 표본 관찰을 전체 데이터의 보장으로 확대하지 않는다.
- 절차 사용량이나 문서 분량을 완성도의 대리 지표로 삼지 않는다.

## 상황별 짧은 위임 예시

### 담당자 답변을 받았을 때 (구현 구간)

```text
답변의 확인된 규칙·근거·미확인을 나누고 바뀐 MD 행만 갱신한다.
각 규칙을 기능·필요 조건·예외·관찰 가능한 성공 기준으로 연결한다.
기존 정책과 충돌하면 표시하고, 내 판단 이유를 만들지 않는다.
```

### 첫 흐름 구현 (구현 구간)

```text
확인된 정책 안에서 [기능 ID]를 가장 단순한 방법으로 입력부터 결과까지 연결한다.
관련 코드·입력·검사를 먼저 확인하고 변경 경계를 정한다.
업무 규칙마다 작은 검사를 두고, 실행한 범위와 미검증을 반환한다.
```

### 독립 검산 (검토 구간)

```text
[결과 파일]을 읽어 필수 F·중요 E의 제약을 해법 코드와 별도로 다시 계산하는 검사를 만든다.
일부러 망가뜨린 결과 몇 개로 각 검사가 FAIL을 내는지 먼저 확인한다.
검사 대상이 0건이면 통과가 아니라 미검증으로 보고한다.
```

### 실패와 수정 제안 (검토 구간)

```text
같은 입력으로 실패를 재현하고 어느 경계에서 달라지는지 확인한다.
제안은 실제 문제·근거·영향·반례·작은 대안·검증에 대조한다.
원인을 확인한 뒤 최소 수정하고 같은 반례와 영향 검사를 실행한다.
제안 자체나 다른 AI의 동의를 실행 근거로 취급하지 않는다.
```

### 문서화 (문서화 구간)

```text
01~05의 실제 기록으로 06_handoff.md를 채운다. 새 사실·이유를 만들지 않는다.
각 줄에 근거 ID를 달고, 문서의 주장마다 실제 검사 T를 연결한다.
근거가 없는 줄은 '근거 없음'으로 표시해 보여 준다.
```

위 경로는 권고다. 원본 런타임 전체 실행·모든 gate 통과와 시험용 제한 적용을 구분한다. 원본의 설치·외부 통신·작업공간 전환·자동 제출을 실행하지 않는다.
