# 세 역할: 구현 · 검토 · 문서화

과제 하나를 역할이 다른 세 세션이 나눠 맡는다. **세션 1이 만들고, 세션 2가 세션 1의 결과를 검토하고, 세션 3이 1·2의 작업을 구조화해 문서로 만든다.** 세 세션은 같은 작업 폴더를 공유하고, 서로의 파일을 읽기만 하며, 자기 파일만 쓴다.

제공 환경에서 세션을 여러 개 열 수 없으면 한 세션이 같은 역할을 차례로 맡는다(아래 ‘한 세션으로 할 때’).

## 공통 규칙

### 파일 소유권

| 세션 | 쓰는 파일 | 읽기만 하는 파일 |
|---|---|---|
| 1 구현 | 과제 코드·결과물, `exam-notes/10_work_log.md`, `00_status.md`·`.operator-state.json`(시간 스크립트), `exam-notes/.evidence-guard/` | `20_review.md`, 01~06 |
| 2 검토 | `exam-notes/20_review.md`, 검토용 검사 파일(`exam-notes/review/`) | 과제 코드·결과물, `10_work_log.md`, 01~06 |
| 3 문서화 | `exam-notes/00_problem_map.md`, `01~06_*.md`, 과제가 요구한 README·보고서 등 문서 | 과제 코드·결과물, `10_work_log.md`, `20_review.md`, `exam-notes/review/` |

- **다른 세션의 파일을 고치지 않는다.** 고칠 것이 있으면 자기 기록에 요청으로 남기고 참가자에게 알린다.
- 검토 세션은 과제 코드·결과물을 고치지 않는다. 결함은 `20_review.md`에 발견으로 남기고, 수정은 구현 세션이 한다.
- 문서화 세션은 코드·판정을 바꾸지 않는다. 결함을 보면 참가자에게 알려 세션 1에 전달한다.
- 세션 2·3이 과제 명령을 다시 실행할 때 출력은 `exam-notes/review/`나 임시 폴더로 보내고, 설정은 복사본으로 바꾼다. 세션 1의 결과물·설정을 덮어쓰게 되면 실행하지 말고 미검증으로 남긴다.
- 연결 스킬이 01~05에 쓰라고 해도 세션 1은 `10_work_log.md`, 세션 2는 `20_review.md`에 남긴다(skill-routing.md 공통 계약).
- **Git 커밋은 구현 세션만 한다.** 다른 세션은 `git status`·`git diff`·`git log` 같은 읽기만 한다. 구현 세션은 체크포인트마다 세 세션의 파일을 함께 커밋할 수 있다. Push는 하지 않는다.
- 같은 파일을 두 세션이 동시에 쓰지 않는다. 기록 파일은 뒤에 이어 쓰고, 다른 사람이 쓴 줄을 지우지 않는다.

### 세션 사이의 연락

세션끼리 직접 말하지 않는다. **파일과 참가자**가 연락 수단이다.

- 세션 1 → 2·3: `10_work_log.md`의 작업 묶음 항목
- 세션 2 → 1: `20_review.md`의 발견 항목. 참가자가 세션 1에 “검토 R3 반영해 줘”처럼 전달한다.
- 세션 3 → 참가자: 기록에 없는 판단 이유를 참가자에게 직접 묻는다.
- 담당자 답변은 참가자가 **세션 1에** 붙여 넣는다. 세션 1은 원문을 작업 로그에 남기고, 세션 3이 그것을 01~03으로 구조화한다.

### 시간

- 잔여 시간은 참가자가 화면에서 확인한 값만 쓴다. 시간 스크립트(`exam_session.py`)는 세션 1만 실행한다. 다른 세션은 `status`(읽기 전용)만 볼 수 있다.
- 남은 30분: 세션 1은 새 기능을 멈춘다. 세션 2는 마지막 전체 재검사, 세션 3은 최종 정리에 들어간다.
- 남은 15분: 세션 1은 제출을 막는 결함의 최소 수정과 저장·제출 확인만 한다. 세션 2·3은 새 작업을 시작하지 않고 마지막 기록만 마친다.
- AI 금지 후속 단계·시간 만료 보고가 오면 세 세션 모두 멈춘다.

### 토큰과 비용

세 세션은 같은 파일을 여러 번 읽으므로 토큰을 더 쓴다. 각 세션은 바뀐 부분만 다시 읽고(`git diff`, 로그 끝부분), 같은 검사를 의미 없이 반복하지 않는다.

## 세션 1 · 구현

목적: 확인한 업무 규칙으로 필수 기능을 끝까지 만든다. 기록 부담은 작업 로그 한 곳으로 줄인다.

1. 과제·자료 확인 → 세션 3의 문제 지도(`00_problem_map.md`)가 나오면 그 질문으로 담당자 인터뷰(`sk-exam-interview`) → 최소 설계·계획(`sk-exam-design` → `sk-exam-plan`).
2. **가장 단순한 end-to-end 먼저**(`sk-exam-implement` ↔ `sk-exam-test`). 업무 규칙마다 작은 검사를 둔다. 판정·계산은 고정 코드로 한다.
3. 필수 기능 완성. 실패는 `sk-exam-debug`.
4. 작업 묶음 하나가 끝날 때마다 `10_work_log.md`에 항목을 하나 추가한다(형식은 양식 참고): 한 일, 바꾼 파일, 실행한 명령과 실제 결과, AI가 스스로 정한 것, 담당자 답변 원문, 남은 것.
5. `20_review.md`에 새 발견이 있는지 체크포인트마다 확인한다. 참가자가 반영을 요청한 발견은 원인 확인 → 최소 수정 → 같은 반례 재검사 후, 작업 로그에 “R번호 반영”으로 남긴다. 반영하지 않기로 한 발견은 이유와 함께 남긴다(이유가 참가자 판단이면 참가자가 말한 그대로).
6. 중요한 AI 수정 제안은 `sk-exam-review-response`로 심사한다.

## 세션 2 · 검토

목적: 세션 1의 결과를 **다른 눈으로** 확인하고, 결함·누락을 발견으로 넘긴다. 같은 코드의 재실행이나 다른 AI의 동의는 검토가 아니다.

**세션 1의 첫 흐름이 나오기 전**에 할 일:
- 과제 원문과 작업 로그의 담당자 답변으로 필수 요구·중요 예외 목록과 **기대값**을 먼저 정한다. 구현을 보기 전에 정한 기대값은 `20_review.md`에 적어 두고, 구현 결과를 보고 바꾸지 않는다.
- 결과 파일을 읽어 제약을 처음부터 다시 계산하는 **독립 검사기**의 뼈대를 `exam-notes/review/`에 만든다. 해법 모듈을 import해 같은 함수로 확인하지 않는다.

**첫 흐름이 나온 뒤** 작업 묶음마다:
1. **AI가 혼자 정한 것 확인**: 작업 로그의 해당 칸과 코드를 대조하고, 업무 결과를 바꾸는 가정이 빠져 있으면 발견으로 올린다.
2. **① 요구 충족**: 누락·오해·요구에 없는 추가.
3. **② 품질·검증**: 독립 검사기 실행, 일부러 망가뜨린 결과로 검사가 FAIL을 내는지 먼저 확인(실패를 못 본 검사는 근거로 쓰지 않음), 검사 대상 0건 = 미검증, 합계가 맞아도 행별 대응 확인.
4. **조건 변경 재실행**: 담당자가 운영 중 바꿀 수 있다고 한 값을 바꿔 결과를 다시 만들 수 있으면 다시 만들어 검사한다. 세션 1의 코드를 고쳐야만 바꿀 수 있으면 발견으로 올린다.
5. **위험 경계**: 입력 검증·권한·민감 정보·저장 복구 중 과제에 있는 것만.
6. 세션 1이 “반영”이라고 적은 발견은 같은 반례로 다시 확인하고 결과를 남긴다.

적용 스킬: `sk-exam-test`(독립 검산·실패 먼저), `sk-exam-review`(통합 리뷰), `sk-exam-verify`(마지막 변경 뒤 재검사). 발견은 양식의 한 줄 형식으로 쓰고, 재현하지 못한 것은 ‘의심’으로 둔다.

## 세션 3 · 구조화와 문서화

목적: 세션 1·2의 작업을 추적 가능한 구조로 정리하고, 과제가 요구한 문서와 인계 문서를 만든다. **새 사실·이유를 만들지 않는다.**

**시작 직후**: 아직 문서화할 것이 없으므로 `sk-exam-frame`으로 문제 지도(`exam-notes/00_problem_map.md`)와 그림을 만든다. 순서는 **참가자가 먼저**다: AI는 자료 사실만 정리 → 참가자가 문제·원인·위험한 가정·질문 3개를 자기 말로 먼저 씀 → AI는 빠진 범주만 짚음 → 참가자가 고르고 고쳐 씀. 모든 가정·질문에 출처(참가자 / AI 제안)를 남긴다. 15분 안팎에 끝내고 참가자에게 알린다. 이후 담당자 답변이 들어오면 지도의 가정 상태만 갱신한다.

체크포인트(첫 흐름, 큰 수정, 검토 결과 반영, 남은 30분)마다:
1. `10_work_log.md`의 담당자 답변을 `01_domain.md`(Q), 요구를 `02_requirements.md`(F), 예외를 `03_exceptions.md`(E)로 구조화한다.
2. AI 제안과 참가자 선택을 `04_decisions.md`(D)로 옮긴다. **참가자의 이유가 기록에 없으면 참가자에게 직접 짧게 묻는다.** 답이 없으면 `참가자 이유 미기재`. 바뀐 판단은 기존 행을 지우지 않고 정정 행을 추가한다.
3. 작업 로그의 실행 결과와 `20_review.md`의 검사 결과를 `05_verification.md`(T)로 연결한다. 검사마다 수행자(세션 1 / 세션 2 / 참가자 관찰)를 적는다.
4. `06_handoff.md`를 갱신한다: 무엇을 만들었나, 시스템 지도(파일·함수·입력→출력), 검토·보강 결과, AI 제안과 검토, 감수한 한계, 최종 상태, 작업 기록 색인.
5. 과제가 README·보고서 같은 제출 문서를 요구하면 그 형식으로 작성한다. 06은 그 재료로 쓴다.
6. 문서의 주장마다 근거(T ID·`파일:함수`)를 단다. 근거가 없는 줄은 `근거 없음`으로 표시하고 참가자에게 알린다. 문서에 적은 실행 명령은 실제로 다시 실행해 확인한다(`sk-exam-verify`).

남은 시간이 15분보다 많으면 참가자가 `06_handoff.md`만 보고 “왜 이렇게 했나 / 무엇을 감수했나 / AI 제안을 어떻게 확인했나”를 채팅에 짧게 써 보게 하고(소리 내어 말하게 하지 않는다), 막히는 곳의 기록만 보충한다. 모범 답변을 먼저 쓰지 않는다.

## 한 세션으로 할 때

세션을 하나만 쓸 수 있으면 같은 파일·같은 역할을 시간 순서로 맡는다. 시간 기준은 [operation.md](operation.md)의 세 구간을 따른다.

| 구간 | 맡는 역할 | 전환 |
|---|---|---|
| 경과 0~100 | 세션 1 구현(처음 15분 안팎은 `sk-exam-frame` 문제 지도) | 필수 기능마다 실행 기록이 생기면 |
| 경과 100~150 | 세션 2 검토(먼저 발견만 모으고, 그다음 구현 역할로 돌아가 보강) | 필수 기능·예외 검사가 마지막 변경 뒤 최신이면 |
| 경과 150~180 | 세션 3 문서화 | 저장·제출 확인 |

한 세션에서도 파일 소유권은 같은 의미로 쓴다. 검토 역할일 때는 코드를 고치지 않고 발견만 모은 뒤, 구현 역할로 돌아와 고친다.
